# Issue #11 — Security remediation review

**Branch:** `security/issue-11-optimistic-concurrency` (Draft PR #22).
**Scope:** B1–B3 and a focused mutation/React conflict audit. Issue #11 remains open. This document is local review evidence; it does not assert exact-SHA GitHub CI or production readiness.

## Corrected findings

- **B1:** The directory and public-profile integration clients now obtain the authenticated owner representation's ETag before legitimate privacy/discovery PATCH requests. Missing `If-Match` is independently asserted as 428; a reused original validator is asserted as 412. Invalid payload cases still reach their intended 400 checks.
- **B2:** Migration 000008 replaces the 000006 membership trigger body and adds a verified-insert trigger. Relevant membership changes invalidate the owner's shared privacy/discovery revision. The existing membership → profile → affiliation order is retained. The old profile is locked *before* checking for another verified membership, so concurrent last-membership revocations cannot each see the other's pre-commit state. The final revocation clears consent and increments the revision in one profile update; reverification never restores consent. A verified insert increments the revision if a profile exists. Onboarding display-name changes increment the profile content revision in the same transaction; idempotent onboarding does not. The legacy internal profile writer also advances content revision for name-only changes.
- **B3:** Removed the duplicate discovery PATCH 428 mapping. A strict YAML duplicate-key parse and OpenAPI 3.1 semantic validation pass. Owner GET/PATCH response ETags and the profile PATCH 404 contract are documented.
- **React cache:** TanStack Query structural sharing is disabled for the three owner resources with non-enumerable ETag metadata. Otherwise, a background refetch could replace a changed response body without its ETag. Privacy conflict recovery loads current server settings for review, preserves the old draft until the user explicitly adopts the current settings, and requires a fresh PUBLIC consent choice when applicable. Discovery's explicit reload is tested with its new validator.

Unconditional service/store methods remain for internal callers and older tests. HTTP profile, privacy/discovery and existing-item history routes call their conditional variants. New callers must not route public writes through unconditional methods. The legacy profile writer now advances content revision even for a name-only edit. Collection/photo routes remain deliberately documented as unguarded pending a separate design decision on collection-level validators. Their existing writes do not change privacy flags or directory consent; PRIVATE withdrawal and public read authorization remain database/server enforced.

## React conflict and privacy audit

- Profile, privacy, discovery and history editors keep the original draft/item validator while mounted. A background refetch does not rebase these drafts. History DELETE uses the exact selected item's ID and revision.
- On 412, profile/history forms and privacy/discovery controls keep entered values. No mutation hook automatically retries. Discovery has an explicit reload; privacy now shows current server visibility and optional flags before the user adopts them. A failed privacy reload retains the draft. Profile/history currently direct the user to close and reopen after reviewing their preserved draft; they do not offer an in-dialog field-by-field merge. A transient background profile-list load error can still replace those editors with the page error view, so draft persistence across that failure needs further UX work.
- A missing owner ETag fails safely with 428. Owner queries are actor-scoped, have no retry, and public caches are removed after successful owner mutations. Public responses use `no-store`; no owner or public body is placed in persistent client storage.
- A new PUBLIC transition still requires explicit checkbox consent. A stale privacy/discovery request cannot restore PRIVATE or withdrawn directory state because both share the checked revision. Membership revocation invalidates that revision before an old draft can commit.

## Migration and release notes

000008 is additive to applied 000001–000007 history. Its down migration restores the 000006 trigger and removes the insert trigger. Down/reapply is suitable for disposable development verification. **Do not downgrade 000008 in a public deployment without an operator-reviewed plan:** the old trigger does not invalidate shared ETags and has the simultaneous last-revocation race. Roll back the application and migration only with writes quiesced and a reviewed consent/ETag reconciliation plan.

The branch still needs exact-SHA GitHub CI after maintainer approval to push. Draft PR #22 must stay draft until formal security review and the collection/photo policy, browser conflict checks, and any required production operations are accepted. The earlier successful CI on a different SHA is not evidence for these commits.

The PostgreSQL/MinIO integration suites, `go test -count=1 ./...`, `go test -race ./...`, `go vet ./...`, and `go build ./...` passed after the backend changes. The new membership test also passed ten consecutive runs. The frontend unit/component suite passed 64 tests across 9 files; the configured oxlint task, TypeScript/production build, strict duplicate-key YAML/OpenAPI 3.1 validation, Compose config, and `git diff --check` passed locally. The new membership test covers owner ETags, two verified memberships, affiliation removal, 412 on old privacy/discovery validators, fresh authorized writes, last loss, reverification, DELETE, rollback, verified INSERT, concurrent revocations and a stale repeatable-read transaction returning SQLSTATE `40001`.

These are local results only. Keycloak browser E2E, Windows accessibility checks, and GitHub CI for the final local commit have not been run in this remediation. Do not mark Issue #11 complete or the branch production-ready from this evidence alone.
