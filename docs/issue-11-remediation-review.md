# Issue #11 — Security remediation review

**Branch:** `security/issue-11-optimistic-concurrency` (Draft PR #22).
**Scope:** B1–B3 plus final photo, collection and React conflict remediation. Issue #11 remains open. This document is local review evidence; it does not assert exact-SHA GitHub CI for unpushed commits or production readiness.

## Corrected findings

- **B1:** The directory and public-profile integration clients now obtain the authenticated owner representation's ETag before legitimate privacy/discovery PATCH requests. Missing `If-Match` is independently asserted as 428; a reused original validator is asserted as 412. Invalid payload cases still reach their intended 400 checks.
- **B2:** Migration 000008 replaces the 000006 membership trigger body and adds a verified-insert trigger. Relevant membership changes invalidate the owner's shared privacy/discovery revision. The existing membership → profile → affiliation order is retained. The old profile is locked *before* checking for another verified membership, so concurrent last-membership revocations cannot each see the other's pre-commit state. The final revocation clears consent and increments the revision in one profile update; reverification never restores consent. A verified insert increments the revision if a profile exists. Onboarding display-name changes increment the profile content revision in the same transaction; idempotent onboarding does not. The legacy internal profile writer also advances content revision for name-only changes.
- **B3:** Removed the duplicate discovery PATCH 428 mapping. A strict YAML duplicate-key parse and OpenAPI 3.1 semantic validation pass. Owner GET/PATCH response ETags and the profile PATCH 404 contract are documented.
- **React cache and conflict review:** TanStack Query structural sharing is disabled for the three owner resources with non-enumerable ETag metadata. On 412, profile, privacy, discovery, experience and education editors hold the original draft/validator, fetch current server values, show field comparisons, and require a chosen-field rebase before an explicit second Save. History DELETE requires a separate review of the current item before a second deletion. Background non-401 refetch errors keep editors mounted. An untouched discovery form can adopt a fresh eligibility snapshot after publication; a changed draft cannot silently gain its newer validator. A new PRIVATE-to-PUBLIC choice requires fresh explicit consent.

Unconditional service/store methods remain for trusted internal callers and older tests. HTTP profile, privacy/discovery, photo and existing-item history routes call only conditional variants. New public callers must not route writes through unconditional methods. The 000007 trigger advances profile content revisions for pointer changes in legacy internal photo operations; the legacy profile writer advances revision even for a name-only edit. 000007 also advances privacy revisions for moderation/visibility changes, while 000008 advances the shared revision on relevant membership transitions in the same database transaction. Collection mutations do not change privacy flags or directory consent; PRIVATE withdrawal and public read authorization remain database/server enforced. Direct SQL outside these entry points remains a trusted-operator boundary and must respect transaction retry on serialization/deadlock errors.

## React conflict and privacy audit

- Profile, privacy, discovery and history editors keep the original draft/item validator while mounted. A background refetch does not rebase these drafts. History DELETE uses the exact selected item's ID and revision. Photo selection captures the profile validator at selection time.
- On 412, the current representation is fetched for comparison but the stale validator stays attached to the draft. Save is paused while the conflict review is open. The owner selects which edits to carry forward; only that explicit action installs the new validator. The owner then saves again. Photo upload/delete similarly requires review before adopting a newer profile validator. No mutation hook automatically retries. Failed conflict reloads and non-401 background refetch errors retain drafts. A 401 refresh still requires authentication. History POST has no stale precondition because it creates a new item.
- A missing owner ETag fails safely with 428. Owner queries are actor-scoped, have no retry, and public caches are removed after successful owner mutations. Public responses use `no-store`; no owner or public body is placed in persistent client storage.
- A new PUBLIC transition still requires explicit checkbox consent. A stale privacy/discovery request cannot restore PRIVATE or withdrawn directory state because both share the checked revision. Membership revocation invalidates that revision before an old draft can commit.
