# ADR 0004 — Identity operations authority and lifecycle (proposal)

Date: 2026-10-25 (Asia/Jakarta).
Status: **Partially accepted for bounded development work; production policy remains proposed.**
Scope: Milestone 5 design. This ADR changes no runtime behavior. See the [M5 plan](../milestone-5-identity-operations-plan.md).

## Context

The development stack imports a Keycloak realm into `start-dev`; the browser uses Authorization Code with S256 PKCE, and the API validates signed access tokens locally. The verified OIDC `sub` maps to `users.oidc_subject`; email is mutable. Membership status and directory consent live in PostgreSQL. `alumnibridge-admin` exists as an unassigned realm role, but there is no administrator operation or grant ledger. Keycloak reset-password is enabled in the local realm; account recovery has not been exercised as an operational procedure. There is no application account-deletion route or lifecycle job. SQL cascades, slug tombstones and photo cleanup cover only parts of deletion.

Offline JWT verification means Keycloak role removal, user disablement and session revocation alone do not immediately invalidate an already issued access token. `GET /auth/me` currently provisions an unknown subject, so erasing the application row while a token remains valid could recreate it. A public profile may also remain visible if the Keycloak account is disabled while the application row is left intact.

## Maintainer direction (2026-10-25)

The maintainer currently operates the early project alone and has not selected production hosting. This supports provider-neutral design and disposable topology tests; it does not appoint a production on-call team. For the current single-operator phase, use a restricted, manual first-grant procedure with explicit operator identity, reason, expiry, and tamper-evident audit reviewed later; do not offer self-service grants or claim independent approval. Before production privileged operations, approve either a genuinely independent second approver or a documented compensating control, with an external review of its risks and an emergency procedure.

## Decision scope accepted for development (2026-10-25)

The maintainer approves a provider-neutral, disposable Keycloak rehearsal and the application access-status baseline described in the [M5 access slice in draft PR #24](https://github.com/sipratama/alumnibridge/pull/24). This includes an additive access-state schema, a fail-closed current-state check on protected routes before implicit provisioning, an issuer/subject block schema without a retention or production writer, and signed-token/PostgreSQL tests. Existing users remain active on backfill. A single maintainer may rehearse restricted manual bootstrap with synthetic accounts; this is not approval to activate production administrator routes or grant real users privileged access.

This approval is limited to development and review of those changes. It does not authorize production hosting, issuer migration, retention/purge, lifecycle status writers, public withdrawal/deletion, admin grants, exceptional recovery/rebind, or deployment. PR #24 needs its own code/CI review and rollout assessment. The existing sub-only user key cannot be silently relinked across issuers.

## Proposed production decisions

1. **Authority.** Keycloak owns credentials, authenticator factors, sessions and the OIDC subject within a particular issuer. The application owns member UUIDs, student/alumni claims, verification, profile publication and deletion state. Treat `(issuer, sub)` as the identity boundary in the production design: the current schema stores only `sub`, so an issuer change requires an explicit migration/reconciliation plan rather than an implicit relink. Email never links or restores accounts. Identity recovery must preserve the original issuer and subject where possible; subject replacement needs an exceptional, audited binding procedure, not automatic email matching.
2. **Deployment.** Use a dedicated production Keycloak realm and database, served through a stable HTTPS issuer behind a configured reverse proxy. Keep the web, API and Keycloak origins and exact callback/logout URI explicit. The API may fetch JWKS over a private route only if tokens retain the same public issuer. Use production Keycloak mode, managed secrets and restricted administration. Do not promote Compose `start-dev`, localhost redirects or the realm import file as a production configuration.
3. **Administrator access.** Treat a narrowly scoped application grant as the current authorization authority for future privileged API calls, checked on every call after token verification. Require the reserved Keycloak role as an additional condition only if the maintainer accepts the resulting two-system provisioning burden. Grant and revoke through a separate trusted operator path with a recorded reason, expiry/review date and restricted audit. In the single-operator development phase, bootstrap the first grant via a documented one-time, out-of-band procedure bound to a known issuer/subject, with least privilege, short expiry, and an auditable record; test it only with disposable accounts. It cannot masquerade as two-person approval. Before production privileged routes, decide whether a distinct approver is available or approve and test a compensating control, including independent review of grants and time-limited emergency use. Bootstrap and emergency authority must not rely on a grant that does not yet exist. No self-service grant, onboarding grant, email-domain grant or automatic alumni verification. A revoked application grant denies a still-valid token immediately; Keycloak role/session revocation is also required. Membership reviewers in M6 need a separate capability and potentially institution scope; the broad realm role must not silently authorize claim decisions.
4. **Lifecycle.** Introduce a durable application access state before exposing deletion. Start deletion by atomically denying protected operations and removing public visibility/discovery/academic consent; then disable the Keycloak account and revoke sessions; only then erase application personal data and request Keycloak removal. Track each external step durably with idempotent retries and restricted, privacy-safe audit. Current `profile_slug_history` retains the literal slug after `user_id` becomes NULL; a name-bearing slug can remain personal data and must not be called anonymous. Approve its purpose, retention and access policy, then choose a lawful non-reuse mechanism (for example, a reviewed one-way lookup representation if it meets the product and privacy requirements) without weakening current reservations during migration. Keep a non-reprovision marker keyed to the approved issuer/subject boundary for a reviewed period that covers token lifetime, backup/restore and subject-recreation risk, or use another proven mechanism; never rely on email or the absence of a user row. Physical photo deletion remains asynchronous through the durable registry and must be monitored to completion. No transaction is claimed across PostgreSQL, Keycloak and object storage.
5. **Recovery.** Ordinary password/factor recovery stays in Keycloak and returns to the same subject. Lost access to all factors or a lost Keycloak user record requires documented identity proof before any subject rebind; production rebind also requires an approved independent approval or compensating review process. Freeze access and privileged grants during investigation. Recovery must never infer ownership from an email address, profile content or self-declared membership. A rebind, if permitted, is an exceptional atomic application change with full audit and publication review; old tokens and subject must remain denied.
6. **Audit and retention.** Record actor, action, target pseudonymous identifier, UTC time, result, correlation ID and approval reference for admin grants/revocations, recovery and deletion. Keep credentials, tokens, proof, reviewer notes, object keys and private contact data out of ordinary logs. Retention durations, legal holds, audit access and erasure exceptions require maintainer/legal approval before implementation. M5 must not invent the M6/M8 verification evidence or appeal policy.

## Alternatives considered

| Option | Assessment |
| --- | --- |
| Reuse local Compose `start-dev` in production | Rejected: development defaults, localhost issuer and imported client settings are not production topology or operational evidence. |
| Self-host dedicated Keycloak versus supported managed hosting | Either can satisfy the proposed boundaries. Choose by operator ownership, upgrade/backup/restore capacity, availability and data residency; product approval is required. |
| Keycloak realm role alone authorizes administrators | Simpler, but locally verified JWT roles remain effective until token expiry. It cannot provide immediate revocation without introspection or a separate current-state check. |
| Application grant alone authorizes administrators | Immediate revocation and narrow capabilities, but Keycloak role becomes informational and operator processes still need strong controls. |
| Require both current application grant and realm role | Defense in depth, with two-system partial failures and a reconciliation burden. Proposed only after explicit approval of the operator workflow. |
| Delete Keycloak identity first | Rejected: public application data can remain published if the database step fails. |
| Delete application user row first | Rejected: a still-valid token can reprovision the same subject; external cleanup may fail. |
| Restore account by verified email | Rejected: email is mutable and may be reassigned or compromised. |

## Consequences and migration

Implementation would need reviewed additive schema for access state, non-reprovision protection, operation progress and a least-privilege grant/audit model. The exact schema and retention design follow approval; do not modify migrations 000001–000008. Existing accounts need an explicit active-state backfill, and existing Keycloak administrators must be inventoried before any role/grant cutover. Enforce current application access state on every protected route, including `/auth/me` and onboarding, before any implicit provisioning; the current `identity.Me` and owner handlers upsert a valid unknown subject. A fresh subject needs a defined enrollment path, while a disabled/deleting/deleted subject must fail closed even when PostgreSQL is unavailable. Keep public reads denied through current publication state throughout deletion. Restrict direct SQL writers and ensure new privileged routes check current grant state on every request without a stale authorization cache. Existing client sessions and token lifetimes need a documented compatibility window. Document the bootstrap and emergency operator path before the first grant; do not treat a single operator's audit entry as independent approval.

For deletion, take the `users` row lock before profile/cascade work, consistent with onboarding and profile writers. Photo activation now takes user before staging/profile after the [owner-write hardening](../milestone-5-lifecycle-race-hardening.md); the [Issue #11 runbook](../issue-11-rollout-rollback.md) retains the historical staging-first deadlock evidence. Direct membership UPDATE/DELETE locks a membership row before its trigger can check the user, so it can still deadlock with a user-first lifecycle transaction. The [membership boundary review](../milestone-5-membership-lifecycle-boundary.md) adds an active-owner trigger but requires trusted callers to lock user before membership and to retry whole transactions on `40P01` or `40001`. A future lifecycle worker must use bounded whole-transaction retry, keep failures pending and alert. Do not replay an old photo `If-Match` or retry only one statement. Recovery rebinds must analyze the same user/profile/membership lock graph before SQL is approved. This factual lock update does not approve a production lifecycle policy.

Rollback after a deletion or subject rebind cannot restore erased credentials, consent or personal data by reversing a migration. Prefer a forward fix while access remains blocked. Schema down is only for disposable databases unless a reviewed data reconciliation and a consistent PostgreSQL/object-store/Keycloak backup exist. A restored profile must not automatically republish, reuse consent or expose a historical slug. Keycloak and application backups must be tested together; independent point-in-time restores can produce orphan subjects or public data.

## Threats and verification obligations

| Threat | Proposed boundary and test |
| --- | --- |
| Stolen or stale token after disable, deletion or admin revoke | Current application access/grant check on every protected/privileged request; signed-token tests before and after state changes, including unexpired old token. |
| Account takeover through email reuse or support recovery | No email-based linking; proof, approved independent approval or compensating review for production rebind, old-subject denial and audit; adversarial recovery drill. |
| Self-granted administrator/reviewer rights | Operator-only grant path, separation of duties, no client role input; forged-token/role and cross-scope tests. |
| Public data persists after external outage | Application transaction withdraws publication before Keycloak step; public profile, photo and directory queries deny during every lifecycle state; fault injection after each step. |
| Lost photo cleanup intent or unsafe rollback | Durable registry and backlog checks; MinIO outage/restart/delete race tests; migration refusal guards. |
| Name-bearing slug or expired deletion marker reidentifies/reprovisions an erased account | Approved literal-slug retention/non-reuse policy; issuer-bound marker tests across token expiry, Keycloak recreation and backup restore. |
| First-admin bootstrap or emergency grant bypasses separation of duties | Disposable single-operator bootstrap drill with restricted audit; before production, test the approved distinct-approver or compensating-control path and timed emergency review. |
| Sensitive operational logs or indefinite retention | Field allowlist, access controls, retention/purge test and backup erasure procedure approved before release. |

## Review gate

The maintainer may review provider-neutral topology, manual operator procedures and disposable tests while operating the early project alone. Before production privileged operations, approve hosting/issuer ownership and issuer-change policy, administrator authority including a distinct approver or explicit compensating control for first-grant and emergency access, deletion eligibility and retention including name-bearing slugs and non-reprovision markers, recovery proof and rebind policy, and audit retention. The single-operator development procedure is not production approval. This partial acceptance is not evidence that production deployment, recovery, deletion or verification operations work. Issue #11 and the existing follow-up issues remain separate release gates.
