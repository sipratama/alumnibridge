## Writer and trigger inventory

The only runtime application INSERT into `memberships` is `identity/postgres.Store.Onboard`: it begins a transaction, locks an **active** `users` row, writes the display name, inserts an active student or pending alumni membership, and may advance the profile content revision. There is no implemented reviewer, transfer, revocation, verified-insert or deletion service. Direct membership UPDATE/DELETE/verified INSERT in Go integration tests and the Issue #11 browser harness are synthetic trusted SQL fixtures, not an authorization path. The public Discovery PATCH writes `profile_directory_affiliations`, not membership status; it already locks active user → membership rows in UUID order → profile → affiliations. Production use of raw privileged SQL still needs a restricted writer and operational authorization design.

Existing migration 000008 has two membership triggers. `memberships_directory_revocation` runs **before UPDATE/DELETE**, after PostgreSQL has already locked the affected membership row. It locks affected profile rows in UUID order, writes the profile to invalidate stale snapshots, increments the shared privacy revision when verification or affiliation data changes, clears directory consent on the final verified loss, and removes old affiliation rows. `memberships_verified_insert_revision` runs **after INSERT** and bumps the owner's profile privacy revision for a verified alumni membership. Migration 000006's profile withdrawal trigger clears directory consent and affiliations on PRIVATE or directory opt-out; migration 000007 advances privacy revisions for publication state changes. Those migrations are not edited here.

| Path | Lock order and result |
| --- | --- |
| Existing onboarding | Active `users` row → membership INSERT → optional profile content revision. The new membership guard rechecks the same row in the same transaction. |
| Raw membership UPDATE/DELETE before this branch | Membership row → profile → affiliation, with no active-user check. A completed `deleting` transition did not prevent another membership write or privacy-revision change. |
| Raw verified INSERT before this branch | Membership insert/FK → profile revision trigger, with no active-user check. |
| Migration 000010 guard | Membership row (for UPDATE/DELETE) → active `users` row → existing profile/affiliation trigger; INSERT checks active user before its verified-profile trigger. Owner transfers check old and new users in UUID order. A non-active owner raises SQLSTATE `23514` before profile/consent side effects. |
| Required trusted caller order | `(issuer, sub)` advisory lock only when identity binding/provisioning is involved; then active `users` row → membership row(s) → profile → affiliations. A future lifecycle transition starts advisory → user → dependent rows. If it touches memberships, its exact dependent-row order and whole-transaction retry need another review. |

The trigger is a fail-closed backstop, not a way to reorder a raw SQL UPDATE/DELETE: PostgreSQL locks its target membership row before any row trigger runs. A raw caller that starts membership → user can deadlock with a user → profile transition, or with Discovery's user → membership path. A trusted caller should lock the active owner first in its **whole** transaction. On `40P01` or `40001`, roll back and retry the entire transaction from authorization and current-state reads; never retry only the failed statement or reuse an earlier consent/ETag decision. The test-only `deadlock_timeout` setting is not a production retry policy.

Migration 000010 permits a cascading membership DELETE when its parent user row is already absent inside the same deletion statement. An explicit membership DELETE while the parent exists but is non-active is denied. The migration is additive after 000009 and has a down migration for disposable verification. Downgrading it with membership writes enabled would reopen the proven gap. The existing single-issuer, sub-only user binding and issuer/subject block retention remain separate decisions.

## Controlled interleavings

The test uses two transaction connections and PostgreSQL lock observation against synthetic users with a verified membership, public profile and directory consent. A synthetic transaction takes advisory `(issuer, sub)` → user → block/status `deleting` → PRIVATE profile withdrawal; it is **not** a production deletion writer.

1. **Transition commits first:** Before migration 000010, a direct membership UPDATE after `deleting` committed successfully. That failing pre-fix assertion stopped before measuring consent, so it proves the post-transition write gap, not a pre-fix consent outcome. With 000010, UPDATE, ordinary INSERT, verified INSERT, and explicit DELETE return `23514`. The membership year and privacy revision stay unchanged after denial; consent, affiliation rows, anonymous profile and Directory publication remain withdrawn. A later synthetic user deletion still cascades through memberships.
2. **Membership commits first with parent lock:** The trusted test transaction locks the active user, then changes the membership. The synthetic transition waits on that user lock and commits afterward. The membership year change is retained, the transition leaves status `deleting` and PRIVATE, and consent/publication remain withdrawn. No deadlock is observed in this order.
3. **Raw membership lock first:** One transaction holds membership and profile while the synthetic transition holds user and waits for profile. The membership UPDATE then asks the new trigger for the user lock. PostgreSQL returns `40P01` for the membership transaction. After rolling back that **whole** transaction, the transition commits. A fresh transaction attempting the membership update reads the new boundary and receives `23514`; it does not change the year or restore consent. The existing repeatable-read membership test also exercises `40001` followed by a full-transaction retry from a fresh snapshot.

The concurrent Directory fixture that changes membership status now takes the active user lock before its membership UPDATE. This makes that synthetic trusted writer follow the same order as onboarding and removes the previously observed Directory/guard lock inversion. Other direct SQL fixture commands run without a concurrent lifecycle transition; they are not approved production writer implementations.

## Verification and remaining gate

Disposable PostgreSQL 17 received migrations 000001–000010. The new test was run once against schema 000009 before the guard and failed as expected: post-transition UPDATE succeeded and the expected deadlock was absent. After applying 000010, its transition-first, parent-first and deadlock/full-retry subtests passed. The full `go test -count=1 -p 1 ./...` suite with `TEST_DATABASE_URL` passed. The first complete-suite attempt exposed a `40P01` in a concurrent Directory SQL fixture; after changing that fixture to lock active user before membership, the complete suite passed. `CGO_ENABLED=1 go test -race -count=1 -p 1 ./...`, `go vet ./...` and `go build ./cmd/api` passed. The first race attempt did not reach Go tests because the disposable container's GCC package download was interrupted; the retry completed and passed. Migration 000010 completed down/up after test fixture cleanup, and the focused membership, existing revision and Directory tests passed on the reapplied schema. `-p 1` keeps database-wide fixture triggers from overlapping across packages; the two-connection tests remain concurrent internally. These results are local evidence at `c6bb6dd1968f8ceebe0e448270fd9bcce70e91b3`, not CI or production deletion approval.

Unexercised boundaries include multi-owner transfer races, arbitrary bulk SQL and mixed isolation levels, real operator authorization, a production lifecycle transaction that locks all dependent rows, Keycloak/object-store failures, backup restore, and release rollback. The trigger does not enforce application role grants or replace a reviewed trusted writer. No retention, issuer migration or legal policy is inferred from this database guard.
