## Actual lock order and transaction boundaries

The verified-token middleware performs `CheckAccess` as a read before calling a handler. It holds no row lock across the handler. `identity.Me` separately calls `Provision`, which takes the advisory transaction lock keyed by `(issuer, sub)`, checks the subject block, and upserts `users` only when the existing row is active. `Onboard` already locks an active `users` row before membership and optional profile-revision writes. All current protected owner routes still use the middleware; the lock below covers the later database mutation when a status transition commits between middleware and the write.

| Path | Lock/write order on `master` before this change | Boundary after this change |
| --- | --- | --- |
| Profile GET with implicit initialization | Read existing profile; if absent, user → slug reservation → profile | The initializing transaction locks and checks active user before slug/profile insert. Existing-profile GET remains a read after middleware. |
| Profile PATCH, legacy and `If-Match` | User → profile → slug reservation → user update, but user status was not checked | Active user → profile → slug reservation → user update, one transaction. Content revision and strong owner ETag change together. |
| Privacy PATCH, legacy and `If-Match` | Single profile UPDATE; PRIVATE trigger withdraws directory consent/affiliations | Active user → profile UPDATE → withdrawal trigger/affiliations, one transaction. |
| Discovery PATCH, legacy and `If-Match` | Membership rows in UUID order → profile → affiliations | Active user → sorted membership rows → profile → affiliations, one transaction. |
| Experience/education append | User → count → child insert, with no status check | Active user → count → child insert. |
| Experience/education update/delete, legacy and `If-Match` | Direct child UPDATE/DELETE only | Active user → child UPDATE/DELETE and revision check in one transaction. |
| Skills add/delete | Add: global skill upsert → user → link; delete: user → link | Add: active user → global skill upsert → link; delete: active user → link. |
| Photo stage/activate/remove, legacy and `If-Match` | Stage: registry insert; activate: staged object → profile → registry; remove: profile → registry | Stage: active user → registry insert; activate: active user → staged object → profile → registry; remove: active user → profile → registry. Failed activation leaves staging for durable cleanup. |
| Onboarding and membership lifecycle trigger | Onboard: active user → membership insert → optional profile content revision. Direct trusted membership UPDATE/DELETE: membership → profile → affiliations; verified INSERT: membership → profile | Onboard remains guarded. Direct SQL membership writers still do not take the active-user lock; their trigger order is unchanged. They require a separate trusted-writer contract before deletion is enabled. |
| Photo cleanup worker | Eligible registry row with `FOR UPDATE SKIP LOCKED` → object delete → registry delete | Unchanged; cleanup must remain possible for non-active/deleted owners. |

The test-only transition takes `(issuer, sub)` advisory lock → user row → subject block/status → profile withdrawal. It sets `deleting`, PRIVATE visibility, clears directory consent, and lets the existing trigger clear affiliation rows and advance the privacy revision. Its SQL is a **synthetic interleaving fixture**, not a production service or approved state transition. A future writer must choose a safe order for membership rows and profile/registry dependencies, and must retry the whole transaction after `40P01` or `40001`. Direct membership SQL currently starts at membership and can conflict with a future writer that starts at user/profile and later takes membership; it can also write after an inactive status unless separately fenced. Do not enable deletion on the strength of the owner-route guard alone.

## Interleavings and observed boundaries

- **Withdrawal first:** An active access check completes; the synthetic transition commits; the old single-statement profile UPDATE succeeds in a rolled-back negative-control transaction. This proves the middleware read alone could not protect dependent-row writes. The guarded profile PATCH and other sampled owner writes return `ErrAccountUnavailable` (HTTP 403 mapping). Content revision remains unchanged, the withdrawal advances privacy revision, consent and affiliations are cleared, and anonymous profile publication returns not found. The real anonymous Directory search includes the fixture before withdrawal and excludes it afterward.
- **Owner first:** A second connection holds the profile row while the owner PATCH holds the active user row and waits. The transition waits for the user row. Releasing the profile lets the PATCH commit first; the transition then commits PRIVATE withdrawal. The owner content revision advances once, the privacy revision advances on withdrawal, consent stays cleared, and anonymous profile and Directory publication are unavailable. The corresponding strong owner ETag follows the content/privacy revision; these two-connection tests assert the counters rather than a concurrent HTTP response header.
- **Photo in both orders:** After withdrawal, activation returns `ErrAccountUnavailable`; the rejected staging row is marked garbage and the existing cleanup path deletes its registry/object. If activation holds the user first, it commits before the transition; the transition then hides the public profile. A later **synthetic direct SQL erasure** detaches the object and the existing cleanup path removes it. No production erasure writer is included.
- **Provisioning in both orders:** A block writer holding the same advisory lock before Provision prevents first creation. In the inverse test, Provision holds the lock and is paused before its insert; the synthetic writer waits, then sees the created user, marks it deleted and inserts the issuer/subject block before commit. Subsequent Provision attempts fail and no active row remains. A marker-only writer would leave an existing active row in this inverse order; the real writer must transition it in the same transaction.
- **Membership serialization:** The existing repeatable-read test produces `40001` for a stale membership transaction. Its new assertion rolls back that transaction, retries the full update on a fresh snapshot, and checks that the discovery ETag changes. This is test evidence for retry scope, not a production retry mechanism.

The current photo activation user-first order eliminates the earlier user/profile/object lock inversion reproduced by Issue #11's old test. The updated test observes activation waiting on the user lock, a successful synthetic deletion, a failed activation, and successful detached-object cleanup. The historical `40P01` evidence remains valid for the old code, but does not describe this branch's photo path. PostgreSQL `40P01`/`40001` can still occur through other trusted SQL orders and future lifecycle steps.

## Verification and limits

The tests use a disposable PostgreSQL 17 database with migrations 000001–000009. They observe row-lock waits through `pg_stat_activity`, use unique synthetic subjects, and remove their user/marker/photo fixtures. The final full `go test -count=1 -p 1 ./...` suite with `TEST_DATABASE_URL` passed; focused two-connection profile, photo, provisioning and membership tests passed. Migration 000009 completed down/up after the tests left zero non-active users and zero blocks; the focused tests then passed on the reapplied schema. `go vet ./...` and `go build ./cmd/api` passed. An earlier full `go test -race ./...` run collided across packages because a Directory fixture temporarily installs a database-wide failure trigger while a Profiles test inserts affiliations. The final `go test -race -count=1 -p 1 ./...` passed, including both integration packages; `-p 1` serializes packages but the two-connection race tests remain concurrent internally. The first failure is a shared-fixture isolation limitation, not a detected Go data race. No branch CI or production environment test is claimed here.

The tests do not cover an approved deletion API, Keycloak disablement, worker idempotence, backup restore, public reads that began before withdrawal commit, production photo storage, or direct SQL writers outside the checked owner paths. Migration 000009 is unchanged. Its issuer/subject block has no approved retention period. The user table remains keyed by `sub` alone; production issuer migration needs a separate design and test. Old API binaries still ignore the new state and must be fenced during any future rollout.
